Guía de estudio del proyecto EasyPark

Resumen de estructura, arquitectura, almacenamiento, Firebase, pruebas y flujo de datos. Esta guía está pensada para estudiar la defensa del proyecto final y ubicar rápidamente dónde se implementa cada requisito.

1. Lectura rápida del proyecto

EasyPark es una aplicación móvil KMP con Compose Multiplatform para gestionar parqueos: registro de usuarios, vehículos, parqueos, espacios, búsqueda de estacionamientos, reservas, historial, ganancias y notificaciones.

Idea principal para explicar en clase: la UI vive en composeApp/src/commonMain, la lógica se separa por Clean Architecture en data, domain y presentation, y la persistencia combina Firebase Realtime Database con Room local.

3. Organización por capas

Capa Qué contiene Carpetas clave Cómo explicarlo
presentation Pantallas Compose, componentes visuales, estados, eventos y ViewModels. */presentation/screen, */presentation/composable, */presentation/viewmodel, */presentation/state Es la capa que ve el usuario. Observa estados con Flow y manda eventos al ViewModel.
domain Modelos del negocio, casos de uso e interfaces de repositorios. */domain/model, */domain/usecase, */domain/repository Define las reglas de negocio sin depender de Firebase, Room ni UI.
data Repositorios concretos, servicios, DTOs, entidades, DAOs, datasources y mappers. */data/repository, */data/service, core/data Conecta la app con Firebase Realtime Database y Room local.
di Módulos Koin para inyectar dependencias. di/DataModule.kt, di/DomainModule.kt, di/PresentationModule.kt, di/InitKoin.kt Evita crear objetos manualmente en cada pantalla; Koin resuelve repositorios, casos de uso y ViewModels.

4. Mapa por requisito de la rúbrica

Requisito Estado Dónde está Qué decir en la defensa
Firebase distribution Parcial gradle/libs.versions.toml, build.gradle.kts, composeApp/build.gradle.kts El plugin de Firebase App Distribution está agregado, pero falta completar configuración de testers, grupos o notas de versión para una distribución real.
Mockups Figma Evidencia externa No se encontró archivo Figma dentro del repo. Se debe presentar el enlace o capturas de Figma aparte si el docente lo pide.
Clean Architecture Cumple Features con data, domain, presentation. La UI no habla directo con Firebase/Room; pasa por ViewModel, casos de uso y repositorios.
MVVM - MVI - Flow Cumple presentation/viewmodel, presentation/state. Los ViewModels mantienen StateFlow, reciben eventos y exponen estados hacia Compose.
Koin Cumple di/DataModule.kt, di/DomainModule.kt, di/PresentationModule.kt. Koin inyecta DAOs, servicios, repositorios, casos de uso y ViewModels.
Pruebas unitarias y UI Cumple commonTest, androidInstrumentedTest. Hay pruebas unitarias de repositorios, ViewModels y mappers; también pruebas UI simples de pantallas Compose.
Firebase Remote Config Cumple App.kt, core/data/remote/RemoteConfigManager.kt. La app lee banderas remotas como mantenimiento y mensaje de mantenimiento.
Conectividad Retrofit REST y/o Room Cumple por Room core/data/db, core/data/dao, core/data/entity. No se usa Retrofit como implementación principal; el requisito se cubre por Room y Firebase Realtime Database.
Notificaciones push / internas Cumple core/notifications, notifications, functions/index.js. FCM recibe push, NotificationHelper muestra notificaciones y la feature notifications lista notificaciones internas.
Manejo de recursos con Localize Mayormente composeResources/values*, tareas syncLoco y downloadLocoTranslations. Hay recursos traducibles en Compose Resources y tareas para Localise/Loco; conviene revisar textos hardcodeados antes de la entrega.
Demo de la app Preparar demo Flujo principal: registro, login, parqueos, reserva y notificaciones. La demo debe mostrar el flujo de usuario conductor y, si aplica, administrador/propietario.

5. KMP: Kotlin Multiplatform

commonMain

Contiene la mayor parte de la app: pantallas Compose, navegación, casos de uso, modelos, repositorios comunes y contratos expect.

androidMain

Implementa lo específico de Android: Firebase SDK, Remote Config, FCM, Room builder, permisos, mapas y MainActivity.

iosMain

Contiene implementaciones actual para iOS y permite que el código común pueda compilar hacia esa plataforma.

En Windows normalmente no se compilan los binarios nativos de iOS, pero la estructura KMP sí está presente.

6. Flujo general de datos

1. Pantalla Compose Muestra información y dispara acciones del usuario.
2. ViewModel Recibe eventos, actualiza StateFlow y emite efectos de navegación o mensajes.
3. Caso de uso Ejecuta una acción del negocio, por ejemplo registrar vehículo o crear reserva.
4. Repositorio Decide si consulta Firebase, Room o ambos.
5. Data source Usa FirebaseManager, servicios DB o DAOs de Room.
6. Mapper Convierte entre DTO, Entity y Model. 
Usuario toca botón
→ Screen/Composable envía Event
→ ViewModel procesa Event
→ UseCase ejecuta regla de negocio
→ Repository usa FirebaseManager y/o Room DAO
→ Mapper convierte datos
→ ViewModel actualiza UiState con StateFlow
→ Compose redibuja la pantalla

7. MVVM, MVI y Flow

Concepto Cómo aparece en el proyecto Ejemplo de ubicación
MVVM La pantalla no contiene la lógica fuerte; el ViewModel coordina estado y casos de uso. */presentation/viewmodel/*ViewModel.kt
MVI Las pantallas usan eventos, estados y efectos: Event, UiState, Effect. */presentation/state/*Event.kt, *UiState.kt, *Effect.kt
Flow Los estados se exponen como StateFlow y algunos efectos como SharedFlow. ViewModels de cada feature.

Frase útil: MVVM organiza responsabilidades; MVI ordena la comunicación; Flow hace reactiva la actualización de la UI.

8. Patrones de diseño usados

Patrón Aplicación en EasyPark Beneficio
Repository Interfaces en domain/repository e implementaciones en data/repository. La lógica de negocio no depende de Firebase ni Room.
Use Case Acciones como login, registro, creación de reservas, consulta de parqueos. Centraliza reglas de negocio reutilizables.
Mapper core/data/mapper y mappers por feature. Evita mezclar datos remotos/locales con modelos de dominio.
Data Source / Service Servicios DB y Firebase manager. Separa el origen de datos del repositorio.
Dependency Injection Koin con módulos de data, domain y presentation. Facilita pruebas y reduce acoplamiento.
expect / actual Contratos comunes con implementación Android/iOS. Permite compartir lógica en KMP sin perder APIs nativas.

9. Almacenamiento local con Room

El almacenamiento en tablas locales se realiza con Room. La base principal está declarada en core/data/db/AppDatabase.kt. Las tablas se definen como entidades en core/data/entity y el acceso se hace mediante DAOs en core/data/dao.

Tabla local Entidad Uso principal
user UserEntity.kt Usuarios registrados o sincronizados.
vehicle VehicleEntity.kt Vehículos asociados a usuarios.
parking ParkingEntity.kt Parqueos disponibles o registrados.
reservation ReservationEntity.kt Reservas realizadas por los usuarios.
space SpaceEntity.kt Espacios de parqueo y disponibilidad.
notification NotificationEntity.kt Notificaciones internas guardadas localmente.
review ReviewEntity.kt Reseñas o valoraciones.

La creación concreta de la base en Android está en androidMain/core/data/db/Database.android.kt. También hay implementación para iOS en iosMain/core/data/db/Database.ios.kt.

10. Firebase Realtime Database

Firebase se usa como base de datos remota en tiempo real. El contrato común está en commonMain/core/data/remote/FirebaseManager.kt y la implementación Android real está en androidMain/core/data/remote/FirebaseManager.kt.

Elemento Función
saveData(path, data) Guarda información en una ruta de Firebase, por ejemplo usuarios, reservas o parqueos.
observeData(path) Observa cambios remotos y los convierte en flujos reactivos.
Repositorios Consumen FirebaseManager para sincronizar datos remotos con modelos de dominio.

Frase de defensa: Firebase es la fuente remota y Room es el almacenamiento local estructurado.

11. Firebase Config, FCM y notificaciones

Remote Config

RemoteConfigManager obtiene valores remotos. En App.kt se consulta app_mantenimiento y mensaje_mantenimiento para mostrar una pantalla de mantenimiento.

Push FCM

MyFirebaseMessagingService.kt recibe mensajes push y maneja tokens FCM. MainActivity.kt solicita permisos de notificación y puede subir el token del usuario.

Notificaciones internas

La feature notifications muestra notificaciones guardadas. También existe NotificationHelper.kt para crear notificaciones locales en Android.

Cloud Functions

functions/index.js contiene lógica backend para enviar notificaciones cuando se crean reservas.

13. Mapas y ubicación

El proyecto implementa mapas usando componentes Android con OSMDroid y ubicación con Google Play Services Location. Aunque la rúbrica mencione Google Maps, el código actual se apoya principalmente en OSMDroid para mostrar mapas.

Pantalla Archivo Uso
Buscar parqueo androidMain/findparking/presentation/composable/FindParkingMapComponent.kt Muestra mapa y parqueos cercanos.
Registrar parqueo androidMain/registerparking/presentation/composable/ParkingMapSection.kt Permite seleccionar o visualizar ubicación del parqueo.
Permisos core/permissions/PermissionManager.kt Gestiona permisos de ubicación según plataforma.

14. SharedPreferences

SharedPreferences se usa en Android para guardar configuraciones simples de la app. Un ejemplo está en MainActivity.kt, donde se usa getSharedPreferences("app_prefs", MODE_PRIVATE) para manejar un indicador de primer lanzamiento o campañas internas.

También se usa una preferencia para configuración de OSMDroid. Para datos del negocio, como usuarios, parqueos o reservas, el proyecto usa Room y Firebase, no SharedPreferences.

15. Serialización

La serialización permite convertir objetos Kotlin a datos transportables o guardables. El proyecto usa el plugin kotlinx.serialization, DTOs serializables y utilidades como SafeSerializers.kt.

Dónde aparece Para qué sirve
core/data/dto Representa datos remotos compatibles con Firebase y conversiones.
core/util/SafeSerializers.kt Ayuda con serialización segura de datos complejos.
navigation Permite pasar modelos o parámetros serializados entre pantallas.

16. Retrofit, Ktor, Room y KSP

En la implementación actual no se observa Retrofit como cliente principal. Sí existe dependencia de Ktor, pero la conectividad real más importante del proyecto está en Firebase Realtime Database y el almacenamiento local en Room.

Tecnología Estado Explicación
Room Implementado Base local con entidades, DAOs y AppDatabase.
KSP Implementado Usado para el compilador de Room y generación relacionada a pruebas/mockative.
Retrofit No usado Si el docente exige Retrofit específicamente, habría que agregar un endpoint REST real. La rúbrica permite "y/o Room".
Ktor Dependencia presente Está como dependencia, pero no parece ser el mecanismo principal de datos.

17. Recursos y Localize

Los textos traducibles viven en composeApp/src/commonMain/composeResources. Existen carpetas como values, values-en y values-fr.

En composeApp/build.gradle.kts hay tareas relacionadas con descarga/sincronización de traducciones desde Localise/Loco. Las pantallas deberían usar stringResource(Res.string...).

Para máxima nota, conviene revisar antes de la entrega si todavía hay textos quemados directamente en pantallas Compose.

18. Pruebas unitarias y pruebas UI

Tipo Carpeta Qué cubren Comando útil

21. Respuestas rápidas para estudiar

Pregunta posible Respuesta corta
¿Dónde se guarda la información local? En Room, mediante AppDatabase, entidades en core/data/entity y DAOs en core/data/dao.
¿Dónde se guarda la información remota? En Firebase Realtime Database, accedido por FirebaseManager y los repositorios.
¿Cómo se evita mezclar Firebase con la UI? La UI usa ViewModels; los ViewModels usan casos de uso; los casos de uso dependen de repositorios de dominio.
¿Por qué usan mappers? Para convertir entre DTOs de Firebase, entidades Room y modelos de dominio sin acoplar capas.
¿Cómo se actualiza la pantalla? Con StateFlow en el ViewModel; Compose observa el estado y redibuja.
¿Cómo se manejan las notificaciones? Con FCM para push, NotificationHelper para mostrar en Android y la feature notifications para notificaciones internas.
¿Qué falta reforzar? Config final de Firebase App Distribution, evidencia Figma, posibles textos hardcodeados y aclarar que mapas usan OSMDroid.
